Part 0

Why This Exists

The billing fact that makes this tool necessary, who it's built for, and the single sentence that describes what it actually does.

0.1 The Problem: A Stopped Instance Still Bills

On most clouds, "stop the server" and "stop paying for it" are the same action. On Linode, they are not. A powered-off Compute Instance continues to reserve its RAM, CPU, and network capacity, and continues to bill at exactly the same hourly rate as a running one. The only action that actually stops compute billing is fully deleting the instance — not shutting it down, not powering it off, deleting it.

That single fact is the entire reason this tool exists. A team that wants to run a development environment only during business hours, a batch-processing fleet only overnight, or a demo environment only when someone is actually using it has no native "pause billing" button to press. The only way to genuinely stop paying is to delete the instance — and deleting an instance normally means losing it: its identity, its configuration, and, if the OS lives on local disk the way a freshly-deployed instance normally does, its data.

Instance Scheduler automates a full delete/recreate cycle and makes it behave like an ordinary stop/start, by making sure everything that makes an instance recognizably "the same machine" survives the cycle on resources that are never touched by the delete: its OS disk, any additional data volumes, its public IP address, and its VPC/VLAN network identity. From the outside, an instance managed by this tool looks like it has a stop button and a start button. Underneath, "stop" deletes it and "start" recreates it from exactly what was there before — and only while it's actually deleted does the compute billing genuinely stop.

0.2 Who This Is For

Any workload that doesn't need to run around the clock is a candidate: development and staging environments used on business hours only, CI/build agents that sit idle most of the day, demo or training environments spun up for specific sessions, batch or overnight-only processing fleets, and standby/failover nodes that only need to exist when actually promoted into service. The common shape is the same in every case — a real, persistent machine identity (data, network address, configuration) that only needs to be *running* some of the time.

It is not a fit for anything that needs to stay reachable continuously, or that can't tolerate the several-minutes-long window a full recreate cycle takes. A production database serving live traffic around the clock gets no benefit from this tool; a dev database that's only queried during working hours does.

0.3 The Core Mechanism, in One Picture

Every instance this tool manages has two states in its own registry: running (a real Linode instance currently exists) and stopped (it doesn't — and nothing is billing for compute). Moving between them is always the same sequence:

Part I

How It Works

What survives a delete/recreate cycle and why, the two Linode networking models this tool has to account for, and the network re-injection mechanism that keeps a recreated instance reachable at the same address every time.

1.1 What Survives, and Why

A delete/recreate cycle only works as a stand-in for stop/start because four kinds of resources are independent of the Compute Instance's own lifecycle on Linode — deleting the instance never touches them.

Storage

Block Storage volumes

A volume is a separate resource from any instance, billed separately (a small per-GB/month rate, far below compute pricing) and completely unaffected by deleting the instance it happens to be attached to. This is why the OS itself has to live on a Block Storage volume, not local disk — see 1.2.

Networking

Reserved public IP

An ordinary instance's public IP returns to Linode's shared pool the moment the instance is deleted. A reserved IP is a standalone resource you own independently — it stays assigned to your account, in its original region, and can be attached to a newly created instance. It carries a small charge while unattached, and is permanently locked to the region it was first reserved in.

Networking

VPC and VLAN identity

A VPC subnet and a VLAN label are both persistent, independent resources — not tied to any one instance's lifecycle. Re-attaching a recreated instance to the same VPC subnet or VLAN, with the same internal address, requires no special preservation step; the resources themselves were never going anywhere.

Metadata

Label, tags, plan, firewall

None of these live on the instance in a way that survives deletion on their own — the tool re-captures the current label, tags, plan type, attached firewall, placement group, and watchdog setting before every stop, and replays them on the very next create, so a recreated instance looks and behaves identically in Cloud Manager and cost reports.

Only one firewall survives a recreate A Linode instance can only ever have a single active Cloud Firewall attached at a time on the older networking model this tool works with — not a limitation this tool introduces, an account-wide constraint from the platform itself. If an instance has more than one firewall attached when it's onboarded, only the first one is captured and replayed on every future cycle; any others are silently dropped. If your instance needs multiple firewalls' worth of rules, consolidate them into one firewall before onboarding.

What does not survive, and has to be actively reproduced every single cycle, is anything Linode treats as belonging to the instance's own creation moment: its network configuration (which interface gets which address), its SSH host identity, and the instance ID itself (a brand-new one is assigned on every create). Parts 1.2 through 1.4 cover how each of those is handled.

1.2 Why the OS Has to Live on a Block Volume

A freshly deployed Linode instance normally gets its own local disk — fast, but tied to that specific instance, and gone the moment the instance is deleted. For a delete/recreate cycle to preserve the operating system and its data, the OS has to be moved onto a Block Storage volume instead, which is then attached fresh to each recreated instance at the same device slot every time.

Boot-from-volume carries a modest performance characteristic relative to local disk, which is why the standard approach — and the one this tool follows — is to build the OS disk locally once, as a golden template, then duplicate it onto a volume rather than installing directly onto Block Storage. Two onboarding paths follow directly from this: a brand-new instance can be provisioned straight from an already-prepared template volume (no migration needed, see Part II.1), while an existing instance already running on local disk needs a one-time migration to move its OS onto a volume before this tool can manage it (Part II.2).

Device order matters for every boot: the OS volume must always be attached at the first device slot, with any data volumes following in their original order, or the instance won't boot from the disk you expect.

1.3 The Two Networking Models

Linode instances use one of two mutually exclusive networking configurations — the older, config-attached interface model, and a newer model where interfaces are managed independently of any boot configuration, with explicit per-address NAT and default-route flags. An instance uses one or the other, never both, and the shape of a valid network configuration differs meaningfully between them (a public IP is delivered via a dedicated interface in one model, or via a NAT mapping with no separate public interface at all under the other).

This tool records which model a given instance actually uses at onboarding time, and reproduces the exact same model — and the exact same public-IP delivery topology — on every single recreate, never defaulting to one or silently translating between them. Getting this wrong for even one cycle would mean an instance that boots successfully but is unreachable, or reachable at the wrong address.

VPC 1:1 NAT A public IP can reach an instance through a dedicated public interface carrying the address directly, or through a VPC's 1:1 NAT mapping with no separate public interface. Both are supported under both networking models. With 1:1 NAT the guest sees only its VPC address and is configured like a VPC-only instance; Linode maps the public address onto it, and the scheduler reaches the instance over its VPC address. Deleting an instance releases an ordinary NAT address but keeps a reserved one, so the tool reserves the NAT address the same way it reserves a public interface's address — when a migration finishes, at onboarding, before every stop, and after a rollback — and reuses it on every start. If reserving fails (it is retried before every stop), the next start asks Linode for a new address and reports it. Under the older (legacy config) model the NAT address is the instance's own public IPv4: a reserved one is given back to the new instance and mapped again, and only one NAT address per instance is supported. A reserved public IP that has since been assigned to another instance, or released from the account, can't be given back to a stopped instance; its start fails immediately with a message naming the address, before anything is created.

1.4 Staying Reachable at the Same Address, Every Time

A recreated instance needs to come back up already configured with the correct static IP, gateway, and subnet — not eventually, not after a manual fix, immediately on first boot.

Linode's own automatic network configuration writes a guest's network interface file once, the first time an instance boots on a given disk, based on whatever address that disk had at that moment. It does not re-run or self-correct when the same disk is later attached to a different instance with a different real address — which is exactly what happens on every recreate cycle, since the instance ID (and often the assigned interface) is new every time even though the disk and its intended address are unchanged.

The fix is to skip relying on that mechanism entirely for anything address-sensitive. At every create, this tool already knows the exact IP, gateway, and subnet each interface should have — it just captured them, or it's re-applying values fixed at onboarding — so it passes that configuration directly to the new instance via cloud-init, which applies it on first boot. Distributions keep network settings in different places, so the configuration ships with a small script that detects which network stack the guest actually runs — systemd-networkd (Ubuntu), NetworkManager (Rocky, AlmaLinux, CentOS Stream, Fedora), wicked (openSUSE), /etc/network/interfaces (Debian, Kali, Alpine) or netifrc (Gentoo) — writes the same address, gateway and DNS servers in that stack's own format, and restarts it. The script never fails the boot; if it can't recognize the stack it leaves the files alone and logs why to /var/log/linode-instance-scheduler-network.log. This runs on every single recreate, for every interface (public, VPC, and VLAN alike, when more than one is present), which is also why a multi-interface instance never ends up with more than one default route: every interface's configuration is stated explicitly, with nothing left to a default-assignment mechanism to guess at.

An instance with no public interface at all — only VPC and/or VLAN interfaces — is supported the same way. Its VPC interface gets its default route via the VPC subnet's gateway (the subnet's first address) and the region's DNS servers (the first three, since Linux reads at most three), matching what Linode's own network configuration gives a VPC-only instance; it simply has no reserved IP. Migrating such an instance off local disk works the same way: pre-flight and verification connect over its VPC/VLAN address, its new boot configuration keeps its own VPC/VLAN interfaces, and no IP is reserved; every migration keeps all of an instance's interfaces, so a public + VPC or public + VLAN instance keeps both. While an instance is stopped it doesn't exist, so Linode treats its VPC address as unused, and a new instance in the subnet can be given it (Linode hands out the lowest free address). Before every start — scheduled, manual or API — the tool compares the instance's recorded VPC addresses with what is in use; if another instance holds one, it moves the instance to a free address in the same subnet (taken from the top of the subnet) and starts it there, reporting the old and new address, with its trusted SSH host key moving along with it. Migrating or onboarding the new instance that was given the address makes the same move first (a stopped managed instance only), so the new instance is never checked against the stopped instance's host key. set-vpc-address (or the instance page's VPC address card) chooses the new address by hand instead, refusing addresses outside the subnet, the gateway, and any address another managed instance or a running instance has; onboarding likewise refuses an instance whose VPC address is already recorded for another managed instance. A private address with no host key on record (after a move, or a lost known_hosts) accepts the instance's key on first contact, as onboarding does; a key that differs from one on record is still refused, and public reserved IPs always use the strict check. Giving other instances in that subnet their own explicit addresses keeps addresses stable. Golden rule: give the instances this tool schedules their own VPC subnet and their own VLAN label, and don't create other instances there by hand. Nothing holds a stopped instance's private address: in a VPC another instance can be given it (the tool then moves the instance at its next start, so it keeps working but changes address), and on a VLAN — where Linode doesn't check addresses at all — an instance given the same address conflicts silently once both run, which nothing can detect. Public IPs never collide, because a managed instance's public IP is reserved. Onboarding warns when an instance's subnet or VLAN already holds instances the tool doesn't manage, and status --check-network repeats the check; the scheduler's own host doesn't count. Because every start ends with a real SSH reachability check, the scheduler must be able to reach that private address — in practice, by running inside the same VPC (or on the same VLAN). VPC 1:1 NAT works the same way under either networking model (see the note above on keeping its public address). An instance whose only interface is a VLAN can't reach Linode's metadata service, so it never receives the per-start network settings; it runs from the settings already on its disk (a VLAN address never changes), and onboarding writes ssh_deletekeys: false to /etc/cloud/cloud.cfg.d/99-linode-instance-scheduler.cfg on the node so cloud-init keeps its SSH host keys across recreates.

VPC and VLAN addresses specifically have to be explicit for the same underlying reason — Linode doesn't run address assignment on a VLAN interface at all, and a VPC's own automatic address assignment isn't guaranteed to hand back the same address on a later attachment, since a recreated instance gets a new hardware identity on every cycle.

1.5 SSH Host-Key Stability

An SSH client that connects to the same address twice and gets two different host keys back will refuse the second connection by design — the entire point of host-key checking is to detect exactly that. A naive recreate cycle would trigger this every single time, since cloud-init normally treats every new instance ID as a fresh machine and generates a brand-new host key on every boot.

This tool distinguishes two cases explicitly. The very first boot of a newly onboarded instance — a fresh clone of a golden template, or the first boot right after migrating an existing instance onto a volume — is allowed to generate a genuinely new key, since that's a real first-contact moment and every clone from the same template needs its own unique key, not a key shared across customers. Every steady-state recreate after that explicitly preserves the existing host key instead, so a managed instance presents the exact same SSH identity across every stop/start cycle, indefinitely.

If you deliberately need to rotate a host key Do it through the tool's own key-rotation command, never by editing its trust store by hand — see Part VI's CLI reference. A steady-state cycle presenting an unexpected key is treated as a genuine security event and refused outright rather than silently trusted; see Part VIII.
Part II

Onboarding

The two ways an instance comes under this tool's management — a fresh instance provisioned from a template, or an existing instance migrated in place — and what each one actually involves.

2.1 Path A — A Brand-New Instance

The simple path: there is no existing instance yet, so there's nothing to migrate.

A golden template — a Block Storage volume already holding a fully prepared OS image — is cloned directly into a new volume dedicated to this one logical instance. The clone is billed from the moment it succeeds, the same as any other volume, and happens exactly once, at onboarding — every later stop/start cycle attaches and detaches that same volume, it is never re-cloned. The new instance is then created against that volume, with a reserved public IP assigned to it (a fresh reservation, or one already held) and its VPC/VLAN addresses chosen once, at this point, never rechosen on a later cycle.

2.2 Path B — An Existing Instance

The path for an instance that's already running on ordinary local disk and needs its OS moved onto a Block Storage volume before this tool can manage it.

This is a real, one-time migration with genuine downtime, not a background operation — it needs a scheduled maintenance window. The sequence: a correctly sized destination volume is created, the instance is booted into Linode's Rescue Mode, and the actual disk contents are copied block-for-block from the local disk onto the new volume. Rescue Mode has no API-level way to execute commands, so the copy runs inside Linode's console (Lish): either you paste the printed command there, or — when a pre-migration backup is kept — the tool does it for you by opening the console over Lish's SSH gateway with this deployment's key and typing the same command, then finishing the migration. The assisted copy needs the deployment's public key in your profile's Lish keys (Profile → LISH Console Settings); the tool only reads your profile to check that, and it refuses without a kept backup, since the backup is what makes an unattended copy safe to undo. Everything before and after that single manual step — sizing and creating the destination volume, entering and exiting Rescue Mode, rebuilding the boot configuration against the new volume, verifying the copy actually took, and converting the instance's existing public IP to a reserved one in place (never swapped for a different address, since DNS and any external allow-lists already point at it) — is handled automatically.

Why the copy command finds the disks itself Inside Rescue Mode, the /dev/sdX letters the original disk and the new volume receive vary between systems, and copying in the wrong direction destroys the original disk. So the command this tool prints never names device letters. It finds the new volume through its /dev/disk/by-id/ link, which names that exact Linode volume, and the original disk as the only other device of its known size. If it can't identify exactly one of each, it copies nothing and lists the devices instead. It ends by printing COPY_DONE or COPY_FAILED.

Two pre-flight conditions are checked before this process is allowed to start at all. First, cloud-init with Akamai's metadata datasource has to already be present on the instance: version 23.3.1 or newer, or an older build that already reports the Akamai datasource (some Linode images ship one with it backported). The network re-injection mechanism in Part 1.4 depends on it, with no fallback, so an instance that doesn't meet this bar needs cloud-init installed or upgraded (or the OS upgraded) during the same maintenance window, before migration proceeds. An image that can't run cloud-init at all isn't supported. Second, if the instance has hand-configured static networking outside Linode's own automatic configuration, that customization is flagged as a non-blocking warning — migration proceeds either way, but any such customization will be silently overwritten by the standard network re-injection on the very next recreate cycle, so it's worth knowing about in advance.

Existing data volumes attached to the instance need no migration at all — they were already independent of the instance's own lifecycle before this tool was ever involved. They're simply captured (which device slot they're in) and carried forward on every future cycle, exactly like a Path A instance's data volumes.

Keeping a backup of the original, and rolling back

The copy is the one step of a migration that can't be undone on its own: once the instance boots from its new volume, the old local disk is deleted. migrate-start --backup (or “Keep a backup of the original first” in the dashboard's migration wizard) gives a guaranteed way back. Before anything is copied, the instance is powered off and Linode's native clone copies it — disks and boot configuration — and each of its attached Block Storage volumes. The clone is kept powered off, with its VPC and VLAN interfaces removed so it can never take or clash with an address while it waits; every setting needed to put the original back (plan, region, label, tags, every interface and address, the public address, which volume sits in which slot) is recorded in the database, in Object Storage when configured, and as a tag on the clone and its volumes.

rollback makes the clone the original system again: it takes back the original public address (kept reserved), its VPC and VLAN addresses, its label, and its data volumes under their original labels — so the original /etc/fstab, which finds volumes by label, mounts them exactly as before — and is booted and checked over SSH. If the original instance still exists (a migration not finished yet), it is replaced: its public address is reserved first, its volumes are detached and kept, and the instance is deleted. An onboarded instance must be stopped first; the scheduler then stops managing the name, and the migrated volumes are kept. Rollback refuses when an original VPC address has since been taken by another instance.

The backup is a billable resource A powered-off Linode still bills at its plan's rate, and each cloned volume bills as Block Storage, until the backup is deleted (backup-delete, or the dashboard's Backups page). Before creating one, the monthly cost is shown from Linode's current price list for the instance's region, and confirmed.

Part III

Scheduling

Individual and group schedules, how the two interact when an instance has both, and the poller that actually enforces them.

3.1 Individual and Group Schedules

A schedule is a set of rules — days of the week plus a start time and a stop time — attached either directly to one instance, or to a schedule group that several instances belong to.

A rule whose stop time is earlier than its start time is an overnight rule: it starts on each listed day and stops at the stop time the following morning (days mon–fri, 22:00 to 06:00, runs every weeknight). The listed days are always the days a window starts.

An instance belongs to at most one group at a time. When both an individual schedule and a group are in play for the same instance, the rule is simple and absolute: an enabled individual schedule always wins outright, and the group's schedule is ignored entirely for that instance, not merged or blended with it in any way. Only when an instance has no enabled individual schedule of its own does its group's schedule take effect. An instance with neither is left under purely manual control — nothing is started or stopped automatically.

Removing an instance from a group never silently leaves it with no schedule at all — the choice is offered explicitly: keep it under purely manual control from that point on, or copy the group's current rules into a fresh individual schedule as a starting point.

When a group's schedule boundary fires, every current member is started or stopped independently — one instance failing (an API blip, a stuck lock, anything else specific to that one node) never blocks, delays, or rolls back the rest of the group. Each member's own outcome is tracked and recorded separately; a group is never treated as one all-or-nothing unit.

3.2 Timezones

Every schedule — individual or group — is defined against a real IANA timezone name (for example America/New_York or Asia/Kolkata), never a fixed UTC offset. A fixed offset would silently drift by an hour across a daylight-saving transition; a named timezone resolves the correct wall-clock behavior automatically on both sides of that transition, with no special handling required from you. A group has exactly one timezone that every member following it inherits — an instance that needs a genuinely different timezone from the rest of its group is a signal that it should have its own individual schedule instead.

3.3 The Poller

A single long-running process checks every managed instance's effective schedule every 15 seconds by default, and again the moment any start or stop finishes, judging the whole fleet against one reading of the clock per check. A check only reads the scheduler's own database; due starts and stops are handed to a pool of workers that lives as long as the scheduler, so a check never waits for a start, a stop or a post-start check to finish, and an instance whose start or stop is still running is never acted on a second time. A start or stop becomes due at its scheduled time and stays due for a catch-up window (one hour by default) for as long as nothing has happened to that instance since that time: the poller acts on it unless a start or stop of the instance — scheduled, manual, or through the API — has already been recorded since. That single rule is what makes the poller robust at fleet scale. A slow cycle, a brief outage of the poller itself, or a failed start (a region temporarily out of capacity for a plan) is simply picked up again — a failed start or stop is retried after a pause of 1, 2, 5 and then 10 minutes rather than on every check — while a deliberate manual action taken after the scheduled time is never overridden. An instance already in the scheduled state is left alone, and when two scheduled times fall inside the window the more recent one wins.

Due starts and stops run in parallel — up to ten at once by default (poll --max-parallel) — so a large fleet due at the same minute is brought up together rather than one instance after another; each still takes its own per-instance lock and records its own audit entry. All workers share one request budget against the Linode API (10 requests per second by default, LINODE_API_MAX_REQUESTS_PER_SECOND); a rate-limited (HTTP 429) response pauses every worker for as long as the API asks, other temporary errors are retried with randomized, increasing delays, and a request that creates something is re-sent only after a 429 — never after a gateway error or lost connection, where it may already have succeeded — so retries can't create duplicates. The interval and window are configurable per deployment (poll --interval-seconds / --window-seconds), with the window required to be at least as large as the interval. When the scheduler is stopped it takes no new work and waits for any start or stop already running to finish before exiting.

The poller is meant to run continuously under your own process supervisor (see Part IX.3 for a systemd example) — it doesn't need to be running for a manual start/stop to work, only for schedules and group memberships to actually be enforced automatically.

3.4 Start Order Between Groups

A group can depend on one or more other groups, so that applications start only after every service they need is up, and stop before those services go down.

Without an order, every instance due at the same time starts independently: an application server can finish booting before its database and fail to connect. Making the application group depend on the database group changes that. When the application group's members are due to start, the poller holds them — reported as waiting on dependency — until every member of the database group is running, is not mid-transition, and, where that group has a post-start check (Part IV.3), has passed that check since its latest start. On the way down the order reverses: the database group's members wait until every member of the application group is stopped.

The wait is re-evaluated on every check, so a held instance starts (or stops) within seconds of the order being satisfied, whatever satisfied it — the depended-on group's own schedule (which may differ from the dependent group's), a manual start, or a slow post-start check finally passing. When the scheduler itself started the depended-on instance, the next check runs as soon as that start, including its post-start check, finishes. A chain is therefore worked through link by link with no idle time between links. The wait is bounded by the same catch-up window as any other scheduled action (one hour by default). If the database group never becomes ready within that window, the dependent group is not started that day. A post-start check that has not reported back is given its own configured timeout plus two minutes before it stops holding dependents.

A one-click start of a group with its dependencies brings up every group it depends on, through every branch, each one only after all of its own dependencies are ready; a stop does the same in reverse.

Part IV

Manual Control & Cost Visibility

What happens when you start or stop an instance yourself, outside its own schedule, and the two numbers this tool shows you for how much a schedule is actually saving.

4.1 Manual Override and Auto-Revert

Manual control and scheduled automation are meant to coexist, not fight each other.

Stopping an instance manually, at any time, needs no special handling — its schedule simply resumes normally at its own next configured boundary. Starting an instance manually outside its configured on-window is the case that needs a deliberate answer, because left alone forever it would silently erode the entire point of having a schedule. The behavior here: a manual start outside the schedule arms an automatic countdown, two hours by default, after which the instance is stopped again automatically unless you explicitly extend it. The countdown is shown plainly wherever the instance's status is displayed, and extending it is a single explicit action — it is never silently renewed on its own.

Keeping an instance running past today's scheduled stop. For an instance running on its schedule (its own or its group's), extend — or “Keep running past today's stop” in the dashboard — skips the next scheduled stop and keeps it running for the chosen number of hours past it (from now, if the stop time has already passed). The scheduler holds the scheduled stop until then and stops the instance when the extension runs out; later days' schedules are unaffected. A manual-only instance, or one with no active schedule, has nothing to extend. A whole group can be extended at once (extend --group-name, or the group page): every running member that follows the group's schedule is extended, while members with their own schedule, stopped or manual-only members are skipped. As with schedules, a node's own extension overrides its group's, whichever was set first, and repeating an extension at the same level never makes it stop earlier. Extending a node or a group also holds the running members of every group it depends on until the same time, so the start order is kept: when the extension runs out the dependent group stops first, then the groups it depends on.

Instances with no schedule at all are never affected The auto-revert countdown only ever arms when a start happens outside an existing, configured schedule's on-window. An instance under purely manual control, with no schedule of any kind, can be started and left running indefinitely with no timer ever attached — that would work against the very point of deliberately choosing manual-only control.

4.2 Savings Shown as a Percentage, Not a Dollar Figure

Two numbers are shown for any instance or group with a configured schedule, and neither is a dollar estimate — contract and negotiated pricing aren't visible to this tool, so any dollar figure it produced would risk being flatly wrong for an account on a non-standard rate. Both are instead a percentage of a full week's hours avoided:

savings % = (1 − scheduled_hours / 168) × 100

Scheduled savings is computed purely from the configured schedule's own hours — visible the moment a schedule is set up, before it has ever run even once. Actual savings is computed retrospectively from real recorded uptime over a trailing window — seven days by default, adjustable per request — and only becomes meaningful once a schedule has been in effect for at least that long. Shown together, the gap between the two is itself informative: a schedule configured for a high savings percentage that isn't being realized in practice is usually a sign that manual overrides are happening more often than the schedule intends.

4.3 Pre-Stop Hooks and Post-Start Checks

Some workloads want a step of their own around every stop and start — a database shut down in a specific, checked way before its instance is deleted, or confirmed to be accepting connections again after it comes back.

A pre-stop hook is a command run once on the instance immediately before it is shut down and deleted; a post-start check is a command run on the instance once it is reachable again. Both run as root over the same SSH access the tool already uses, and both apply to every stop and start regardless of what triggered it — a schedule, a person, the API, or the automatic stop at the end of a manual-override window. They're configured per instance or per group; an instance's own hook overrides its group's for that hook type only, so an instance can set its own post-start check while still using its group's pre-stop hook.

Every stop already performs a graceful operating-system shutdown before deleting the instance, so services managed by the operating system's own service manager are stopped cleanly with or without a hook. What a pre-stop hook adds is an explicit step whose result is checked — and the option to refuse to delete an instance whose shutdown step didn't succeed.

4.4 Manual-Only Nodes and Scripted Control

Some instances shouldn't follow any schedule; they're started and stopped by people or by your own automation. The tool treats that as a first-class mode, with the pieces a script needs.

Manual-only mode. An instance set to manual-only (set-mode --manual) is never started or stopped by the poller and never gets an auto-stop timer. To keep the two kinds of control from conflicting, a manual-only instance can't have its own schedule and can't belong to a group that has one; it can belong to a group with no schedule, for shared hooks or a start order. The mode is recorded on the instance's OS volume and restored by rebuild.

Whole-group actions. start/stop --group-name (and POST /groups/{name}/start|stop) act on every member in parallel, each succeeding or failing independently. With dependencies included, a start brings up the groups the target depends on first and waits until they're ready — post-start checks included — and a stop brings the dependent groups down first. A stage that doesn't fully succeed stops the chain; later groups are reported as skipped rather than acted on out of order.

Respecting start order. A one-off start or stop proceeds with a warning when the instance's start order isn't satisfied. With --respect-dependencies (or "respect_dependencies": true over the API) it's refused instead, before anything is touched — exit code 5 on the command line, HTTP 409 over the API.

Predictable results. start and stop exit 0 when the instance is in the requested state (including already being there), 1 on failure, 3 when another operation holds the instance, 4 for a changed SSH host key, and 5 for a start-order refusal. --json prints one JSON object on standard output, with progress on standard error. Over the API, ?wait=true returns the finished result in the same response instead of an operation id to poll.

4.5 Holidays

A holiday keeps infrastructure down on a date it would normally run, without touching any schedule.

A holiday is a date — or a range of dates — that applies to every node, to the members of one group, or to one node. On that date, judged in the timezone of the schedule that would start the node, the scheduler skips the node's scheduled starts. Scheduled stops still happen, so anything left running the evening before is shut down as usual, and the next ordinary day starts on schedule with nothing to undo. Manual and API starts are never blocked. Removing a holiday during the day lets a start that was skipped earlier that day catch up, within the usual one-hour window.

A holiday added for every node is account-wide. A group that must keep running can ignore account-wide holidays; its members then start as usual on them, while holidays added for that group or one of its nodes still apply. Each node can also follow or ignore account-wide holidays itself, and — as with schedules — a node's own choice always overrides its group's; without one it inherits the group's (or follows the calendar if it has no group). These settings live in the database, in tags on each node's OS volume and in the group's Object Storage record, so they come back with restore and rebuild.

Holidays are managed on the dashboard's Holidays page (each group's page has a Holidays card with its upcoming holidays, adding a date or range for the group, Run on account-wide holidays and Skip tomorrow; each node's page has an account-wide holiday choice), with holiday-add / holiday-remove / holiday-list / holiday-settings, or through the API (GET/POST/DELETE /holidays, PUT /groups/{name}/holiday-setting, PUT /instances/{name}/holiday-setting). A node shows when today is a holiday for it. Holidays are part of the database snapshot and are mirrored to Object Storage, so restore and rebuild bring them back.

Part V

Disaster Recovery

What happens if the local registry that tracks every managed instance is lost or corrupted — and the honest limits of how much of it can actually come back.

5.1 The Registry, and Why It Can Be Rebuilt From Nothing

Every managed instance's identity — which OS volume, which data volumes, which reserved IP, which schedule, which group — lives in one local database. Losing that file would normally mean losing the only record of which real Linode resources belong to which logical instance, with no way to reconstruct it.

This tool avoids that with two independent, layered backups, neither of which the local database ever depends on to function day to day. The first is Linode's own resource tags: the same identifying information is written directly onto the OS volume, each data volume, and the reserved IP themselves, every time an instance is onboarded, started, or stopped — so tags removed or edited out of band are put back within one start/stop cycle. The second, optional layer is Object Storage: a single, complete backup of everything about the instance that tags can't hold, written to a bucket you control. The local database is always the fast, authoritative source of truth for day-to-day operation — recovery only ever reads from tags or Object Storage when that database itself is gone or unreadable, never otherwise.

Who answers "what's the truth" at any given moment The local database, without exception, whenever it's readable. Tags and Object Storage are never consulted during ordinary operation — not by the poller, not by a manual start or stop, not by the dashboard. They exist purely so the recovery command has somewhere to read from on the one occasion the local database itself is the thing that's broken.

5.2 What's Stored Where, and Why

Not everything about an instance is backed up the same way. Each piece of data goes wherever is cheap enough to be worth it, without ever pretending a size- and shape-constrained system like a resource tag can hold something it structurally can't.

Linode tags hold instance identity (which OS volume, which data volumes, which reserved IP), individual schedules, schedule-group membership and definitions, a simple single-network-interface configuration, and a reference to any SSH key that's also registered directly on the Linode account. Tags are free, visible directly in Cloud Manager, and survive independently of this tool's own database entirely — but each one is capped at fifty characters, a single resource can only hold a bounded number of them, and there is no way to write to more than one Linode resource at once as a single atomic operation. That combination makes tags the right home for small, fixed-shape facts, and the wrong one for anything of unpredictable size.

Object Storage, if configured, holds a single complete backup of everything else: a multi-interface or VPC/VLAN network configuration, an SSH key that isn't registered on the Linode account under any name, the instance's plan/firewall/placement-group/maintenance-policy/watchdog settings, its label, and its own Linode tags (the customer's own labeling tags, distinct from this tool's disaster-recovery tags). One plain record per instance, no size constraint, no bespoke encoding required — the tradeoff is that it's an optional layer a deployment has to explicitly set up, not something that exists automatically the way tags do.

Two things are recoverable through neither mechanism: a manual-override auto-revert timer, and the audit/history log. Both live only in the database — and with Object Storage configured, the database itself is uploaded within about a minute of every change (5.7), so in practice they come back too, as of a minute or so before the loss. 5.6 explains what's at stake without Object Storage.

5.3 Recovering a Stopped Instance

An instance that was genuinely running at the moment local state was lost recovers completely, always — everything about it, including its live network configuration and SSH access list, is simply read fresh off the running instance itself. A stopped instance has nothing live to read from, so it depends on what was captured and backed up the last time it was stopped or onboarded.

Recovery for a stopped instance follows a fixed order, and never guesses. First, the account is scanned for tagged resources by name — this is where identity comes from, always, and nothing later in the process ever overrides it. Second, the OS volume's own tags are read for a schedule, group membership, and, if the instance's network configuration was simple enough to tag-encode, that configuration itself, plus a reference to any SSH key that's also a registered key on the Linode account — that reference is resolved back to the key's actual current content by looking it up on the account directly, not by trusting a stored copy. Third, if Object Storage is configured, the instance's full backup record is fetched and used to fill in whatever tags didn't already provide — an individual schedule whose tags are missing or unreadable, a more complex network configuration, an SSH key with no account match, plan and firewall settings, label. Object Storage is consulted last and only ever fills a gap; it's never allowed to override what the tag scan already established for identity.

Once a network configuration and at least one SSH key are known — by any combination of the sources above — the instance is reported as fully recovered, with its status restored to stopped, ready to start normally exactly like one that was running. If, after all of that, either is still missing, the instance comes back with its identity correctly restored but its status set to needs_manual_recovery — a plain marker that one step is still outstanding: boot it once from its recorded volume and address, then hand it back to the tool the normal way (running onboard again completes the recovery).

A third status: unreachable Separate from disaster recovery, an instance can also show unreachable in day-to-day operation — either right after a create, before the first network reachability check has succeeded, or when an already-running instance is found powered off out-of-band (through Cloud Manager, not through this tool). Either way, the fix is the same: run start again. The tool detects a confirmed-gone or genuinely powered-off instance automatically and completes the recovery, rather than creating a second, duplicate one.

5.4 Durable, Verified, Self-Healing Writes

Every stop or onboard writes the instance's newly captured state in two separate steps, to two independent systems — and those two steps are deliberately not, and cannot be, one atomic operation.

The local database write happens first, and it is real, immediate, and fully in effect the moment it succeeds — this is the one write every day-to-day operation of the tool actually depends on. The tag and Object Storage backups happen as a separate, second step, right after: each one is written, then read back and compared against what was just sent, and retried automatically on a transient failure. That verify-then-retry discipline exists because a write that appears to succeed isn't always trustworthy on its own — reading it back is the only way to be sure.

What isn't attempted is making the local write and the backup writes succeed or fail together. Two independent systems — a local file and a remote store — have no shared way to guarantee that; promising otherwise would be promising something this design can't actually deliver. What's guaranteed instead is durability without that guarantee mattering in practice: a backup failure never blocks or reverses the real operation (the local database write has already happened by the time a backup is even attempted), and it never needs to be manually tracked or retried, because the very next time that instance is stopped or onboarded again, its entire current state is backed up again from scratch. A single missed backup corrects itself on the next ordinary use of the instance — that's what "self-healing" means here: not that a failure is detected and repaired by some separate watcher process, but that the next routine write is always a full, current snapshot, never a partial update, so there's nothing stale left over to repair.

The same applies to the recovery tags themselves. A change to a schedule, a group, a start order or a node's manual-only setting is written to the database first and then to the OS volume's tags; if that tag write fails, the change still takes effect and a warning is shown. Every start and every stop then rewrites those tags from the database, along with the instance's identity and hook tags, so a missed tag write — or a tag edited or removed in Cloud Manager — is corrected the next time the instance starts or stops, without anyone repeating the change. An individual schedule is also kept in the instance's Object Storage record, refreshed whenever the schedule changes, as a second copy beside its tags.

5.5 Recovering From a Corrupted or Lost Database File

A missing database file and a corrupted one are handled differently on purpose, because they mean different things.

A missing file is the easy case: the tool creates a fresh, empty database automatically the next time it runs, no special action needed at all beyond then running the recovery command described below. A genuinely corrupted file — present, but not a valid database — is detected specifically and distinguished from an ordinary momentary lock conflict between two processes; the tool refuses to proceed with a clear, direct message rather than behaving unpredictably against a file it can't actually trust.

Recovering from a corrupted database file Move the corrupted file aside (its exact location is named in the error message itself). Run the recovery command once. A fresh, empty database is created automatically, and the command reconstructs every managed instance's identity, individual schedule, and group membership from tags — plus, for any instance with a usable tag-based or Object Storage backup as described in 5.2–5.3, its full network configuration and SSH access too.

Nothing about this recovery path is destructive to the real infrastructure it's recovering the record of — the instances, volumes, and reserved IPs it reconstructs a registry entry for were never touched by the loss of the local file in the first place. The recovery command only ever reads and reconstructs; it never deletes or recreates anything on the Linode side as part of this process.

5.7 Moving to a New Host

If the host running this tool is lost, a replacement can take over with everything it was doing — from a backup when there is one, from Linode tags and Object Storage when there isn't.

Three things live only on the deployment host. The database holds every instance, schedule, group, hook, start order, API token and the audit history. The trusted host-key file records each managed instance's SSH host key, which every start checks strictly. The deployment SSH private key is the one key every managed instance trusts. The backup command, on a timer, takes a consistent database snapshot and a copy of the trusted host keys, to Object Storage and/or a local directory; with Object Storage, the scheduler also uploads a fresh snapshot within about a minute of every change, so a lost host loses at most about a minute. Old snapshots are pruned: everything from the last two days, then one a day for thirty days — never the newest.

The SSH key is kept recoverable automatically. It's encrypted on the host (AES-256-GCM, with a key derived by scrypt from a passphrase generated at install) and stored in the database — so every snapshot carries it — and in Object Storage; its public half is registered under the Linode profile's SSH keys; and the passphrase is kept in a private StackScript in the Linode account. A replacement host fetches the passphrase with the API token it needs anyway. Optionally, the operator's own age public key adds a copy only the operator can open: the whole settings file (API token, bucket keys, OAuth and alert settings) and the SSH key, encrypted to that key in Object Storage and re-uploaded whenever either changes; the host can write it but never read it back, and a replacement host then needs only the bucket settings and the operator's age identity. The escrow adds no new way in: a full-access Linode token can already gain root on every instance through rescue mode, a root password reset or Lish, and the passphrase opens nothing without the encrypted key, which needs the Object Storage keys or a snapshot.

install.sh recover sets up a fresh host and puts all of it back before starting anything: it decrypts the SSH key, restores the newest database snapshot and the trusted host keys, runs the tag-and-Object-Storage reconstruction described in 5.3 to add anything onboarded or changed after that snapshot without disturbing what the snapshot restored, and then the self-healing check (5.8), which reconciles the snapshot with the account. Only then are the poller and API started, after which any node left off its schedule by the outage is listed for approval. With --no-start it stops short of starting so the result can be reviewed first.

When the whole host is gone. A dead host can't report itself, and Linode's resource-usage alerts fire only when usage goes above a threshold. One active scheduler. The active scheduler holds a lease in Object Storage, renewed every thirty seconds and expiring after three minutes. A second scheduler — an old host coming back after a new one took over — finds the fresh lease and stands by: it starts, stops, heals and uploads nothing, and raises an alert. recover takes the lease over at once, a cleanly stopped scheduler gives it up, and scheduler-lease --take-over moves it deliberately. A standby host also refuses changes made on it: its API answers 409 to anything but reads (and the take-over itself), and the CLI refuses commands that change nodes, schedules or settings — two hosts changing the same nodes could undo each other. LIS_ALLOW_STANDBY_CHANGES=1 overrides this. When the bucket can't be reached, the scheduler that was active keeps scheduling, so a bucket outage never stops the fleet, while a host that wasn't active stays standby, since it can't tell whether the other one is still running; scheduler-lease --take-over overrides that too.

Restore testing. Every day the newest snapshot is downloaded and checked — checksum, SQLite's integrity check, age, and that it holds every node — and the stored key copies are decrypted against the real key, all without touching the live database. A database that fails the integrity check is never uploaded, so a damaged copy can't replace a good one. An upgrade takes a snapshot with the old code first.

5.9 Deletions Wait Out a Grace Period

Offboarding a node, or deleting a pre-migration backup, takes it out of management at once — but nothing on Linode is deleted until a grace period has passed, and until then it can be brought back exactly as it was.

When offboard or backup-delete runs, every resource involved keeps all of its tags — ownership, schedule, group, hooks — and gains two more: lis-pending-delete:<date> (or lis-pending-untag:<date> on a volume that will be kept rather than deleted) and lis-pending-of:<name>. The grace period is seven days by default (LIS_DELETION_GRACE_DAYS; 0 deletes at once), and --now on either command skips it. When an entry is due, the active scheduler carries it out, re-checking each resource first: anything that's no longer marked, that has since been attached or assigned to an instance, or that another name now claims is left alone.

5.10 Proving and Protecting Recovery

Backups only matter if a new host could actually use them. Several mechanisms keep that true without anyone having to remember to check.

A copy of the release in the bucket. Installing on a new host normally fetches this tool from GitHub, its Python dependencies from PyPI and Node.js to build the dashboard. So that a recovery depends on none of them, the scheduler keeps the installed release in the deployment's own bucket — the code, the built dashboard, requirements.lock, and a wheel of every dependency for the host's platform — at deployment/release/<version>.tar.gz and deployment/release/latest.tar.gz, uploaded whenever the installed code changes and again if removed (release-backup on demand). Fetched with any S3 tool and the bucket keys and extracted, its install.sh recover installs with no download from GitHub, PyPI or Node.js, falling back to PyPI only if the bundled wheels don't fit the new host's platform or Python.

Hash-locked dependencies. Every Python dependency is pinned in requirements.lock with its SHA-256 hashes, and both install.sh and the container image install with --require-hashes, so a host only ever installs exactly the files that were released.

Bucket versioning. When backups are configured, versioning is turned on for the bucket, with a lifecycle rule expiring old versions thirty days after they were overwritten or deleted (other lifecycle rules on the bucket are kept); the health check turns it back on if it's found off. An overwritten or deleted backup stays recoverable for those thirty days: bucket-protection --key KEY lists an object's versions and --restore-version VERSION_ID makes one current again. The bucket's access key needs permission to change bucket settings; if it doesn't, an alert says so.

Restoring one item. To undo a mistaken change to one node's schedule or hooks, or to one group, restore-item puts back just that item from a snapshot — the newest in the bucket, a chosen one, or a local file — without touching anything else. A missing group is recreated with its schedule, holiday setting, hooks and start order; --with-members also re-adds members that exist and aren't in another group. The dashboard shows the snapshot's version next to the current one before restoring.

Recovery drills. The daily restore test (5.8) proves the backups open; a drill proves a new host could take over. recovery-drill creates a throwaway g6-nanode-1 tagged lis-recovery-drill, copies the release copy and a minimal settings file onto it, and runs install.sh recover --drill: the latest snapshot and the deployment key are restored, then recovery-drill-check verifies that every node's volumes and reserved IP exist and every running node answers over SSH with the restored key. A drill host is read-only — it takes no lease, doesn't rebuild or heal, uploads nothing and starts no services — and the VM is always deleted afterwards. Each drill costs a nanode for about ten to fifteen minutes. With LIS_RECOVERY_DRILL_DAYS=7 the scheduler runs one weekly, and a failed or missing drill is alerted.

Rotating credentials. rotate-credentials replaces a credential that may have leaked, with no downtime:

CredentialHow it's replaced

7.2 Authentication: Two Credentials, Two Jobs

The API supports "Login with Linode" — your team signs in with the exact same account credentials they already use for Cloud Manager, rather than a separate shared secret.

This login token answers exactly one question — who is calling right now — and is never used to talk to Linode's own API directly. A completely separate Linode API token, configured once by whoever deploys the tool, is what actually performs every real operation. This separation is deliberate: the scheduler has to keep running and firing scheduled actions even when nobody is logged in, which only works if the credential doing the real work isn't tied to any one person's login session.

The session token produced by logging in isn't tied to a browser either — it's a plain bearer token, sent the same way (an Authorization header) whether the caller is the dashboard or a script. Scripts and pipelines use an API token instead.

API tokens. A named token is created by an administrator (api-token-create, or the dashboard's API tokens page) and shown exactly once; only a hash of it is stored. Each token carries one or more scopes — read (lists, status, history, savings, activity, schedules, groups, hooks, pending deletions, snapshots, system status), operate (start, stop, extend, group start/stop, run a hook, clear a stuck mark, catch up missed schedules, run a backup, save the release copy), configure (schedules, groups, membership, start order, manual-only mode, VPC address, recover a pending deletion, restore one item, bucket versioning, recovery drills, system settings) and admin (everything else, including hooks, which run as root, onboarding, migration, offboarding, deleting a pending deletion now, rotating credentials, logs and token management) — and, for a token meant to do exactly one thing, single operations instead — for example instances:stop, groups:start, schedules:write, mode:write, hooks:run, instances:onboard, tokens:manage, system:read, system:backup, system:configure, deletions:read, deletions:recover, deletions:delete-now, backups:read, backups:restore-item, backups:release-copy, backups:versioning, backups:drill or credentials:rotate (settings holding credentials — Object Storage keys, the SMTP password — stay admin-only; the full list is printed by api-token-scopes; a token holding tokens:manage can never create a token wider than itself). Tokens can be limited to particular instances and groups — manual-only instances included, which such a token can then start and stop — in which case lists show only what it covers and it can read only the operations it started. On the dashboard's API tokens page, instances and groups are picked from searchable lists of what exists, and the operations offered come from the server (GET /tokens/scopes). The scope a request needs is derived from the route itself, and any route not explicitly classified requires admin, so a narrower token can never reach new functionality by accident. Tokens can expire, can be revoked at any time, and every action taken with one is recorded in the instance's history under the token's name.

7.3 The Web Dashboard

A browser-based dashboard, served by the same API process, covers the full day-to-day surface: signing in, viewing and onboarding instances, configuring individual and group schedules, starting and stopping instances manually (with the auto-revert countdown shown plainly when active), managing group membership, configuring pre-stop hooks and post-start checks (with each instance's recent hook activity), both savings percentages, a Pending deletion page for recovering an offboarded instance or deleted backup, or deleting it now after typing its name (5.9), and, on the System backup page, restoring one item from a snapshot after comparing it with the current one (5.10). Path B migration (Part II.2) can be driven entirely from the dashboard, not just the CLI — a guided flow walks through the same pre-flight checks, starts the migration, then presents the manual copy step directly in the browser: paste the guest's own device listing to confirm the correct disks before copying, run the copy in the Lish console as usual, then paste its output back in to verify and complete the migration. The same one-time SSH password/key fallback described in Part VIII.1 is available here too, for a node that doesn't yet trust this deployment's key.

Three pages show what the backend is doing without a terminal on the scheduler host. Activity lists everything the backend did, newest first and updating live: every start, stop, onboard, offboard, migration step and hook run, whether scheduled, manual or from the dashboard, with every warning and error they reported; each scheduler decision (fired, waiting on a dependency, failed); and every console command with who ran it. Part VIII

Security

How SSH access, host-key trust, and the two credential types are handled.

8.1 One SSH Keypair, Never a Stored Credential

SSH access is needed on an ongoing basis — to verify real reachability after every recreate, and to re-read the current authorized-keys list before every stop so a departing team member's revoked access isn't silently reinstated on the next cycle.

This never requires storing a customer's root credential anywhere. One SSH keypair belongs to the deployment itself — its private key lives only on the server running this tool, read fresh at each use, never written into the database. For a brand-new instance provisioned from a template, this deployment's public key is simply baked into the template once, with no credential ever exchanged. For an existing instance being brought under management, you add this deployment's public key yourself, the normal way you'd add any key — through access you already have.

The same SSH access carries pre-stop hooks and post-start checks (Part IV.3), which run as root. Anyone permitted to set a hook — from the CLI, the API, or the dashboard — can therefore run a root command on that instance, which is why every hook change is recorded with who made it and the full command, and why dashboard access deserves the same care as shell access to the instances themselves.

A one-time fallback exists on the onboarding screen for a customer who'd rather hand over temporary access than add the key themselves — a password or a private key pasted directly into the form. Neither is ever written to the database: a pasted password is used once, for that single request, and discarded; a pasted private key is written to a locked-down temporary file, used once, and deleted immediately afterward regardless of whether onboarding succeeds or fails.

The keypair can be replaced at any time with rotate-credentials ssh-key (5.10): no node is ever left trusting only a key the deployment no longer has, because the old key is withdrawn from each node only after a login using the new key alone has succeeded on it.

8.2 Host-Key Trust Fails Closed

Every steady-state reachability check verifies the presented SSH host key strictly against the one recorded for that instance (see Part I.5) — a mismatch is refused outright, exactly the way an ordinary SSH client would refuse it, rather than silently accepted. A genuinely new host key is only ever trusted at a deliberate first-contact moment (initial onboarding, or an explicit, operator-run key rotation) — never automatically during ordinary operation.

Part IX

Deployment Model

Who runs this, on what, and why the design choices fit that model.

9.1 Self-Hosted, One Deployment Per Account

This is a tool you run yourself, against your own Linode account — not a shared service operated on your behalf.

Every design choice downstream of this follows from it. The local registry is a single SQLite database file — no separate database server to stand up, secure, or back up, appropriate for a single-tenant, self-hosted deployment where the alternative (a full relational database server per customer) would be a heavy, unjustified operational ask for what's meant to stay a lightweight tool. If you register a dashboard login, it's your own OAuth application registered in your own Linode account — there is no shared vendor infrastructure of any kind in the credential path.

9.2 High Availability, the Appropriate Way for This Workload

This tool's availability model is built around fast, safe recovery rather than redundant, always-on replicas — a deliberate choice, not the absence of one.

An active-active setup (two or more scheduler processes running at once) and an active-passive setup (a hot standby ready to take over) both solve the same underlying problem: keeping a system reachable and correct through the brief window while one instance of it is down. Neither problem actually exists here in a way that justifies the cost of solving it. The scheduler's whole job is to notice a scheduled boundary has been crossed and fire a start or stop — it evaluates on a short, fixed interval with a tolerant matching window (typically a few minutes either side), not on every incoming request the way a system serving live traffic does. If the process is briefly down — a crash, a host reboot, a deploy — the next scheduled action simply fires a few seconds late, once an ordinary process supervisor brings it back up; nothing downstream notices or breaks, since nothing downstream is waiting on it in real time. Manual control (the CLI and, if you run it, the REST API and dashboard) works independently of the scheduler the entire time regardless — an operator is never blocked from starting or stopping a node by hand just because the scheduler happens to be restarting.

Active-active would trade that brief, harmless delay for a real correctness risk instead: two scheduler processes with no genuine coordination between them (a distributed lock, a leader election, a consensus protocol — the actual infrastructure "active-active" implies) could both decide the same instance is due for the same action at the same moment and race each other, or worse, one could fire a start while the other is mid-firing a stop for the same node. That's a new failure mode this tool would be introducing to solve a problem — a few seconds of scheduler downtime — that a plain restart already solves for free. Active-passive avoids the double-fire risk but still needs its own machinery to be worth anything: health checks to detect the primary is actually down (not just slow), a way for the standby to agree it should now be the one acting, and a shared or replicated view of state so the standby doesn't start from a blank slate. All of that is real, ongoing infrastructure with its own failure modes, kept running and paid for at all times, to protect against an outage that a single supervised process already recovers from in the time it takes to restart.

This is also, directly, a cost decision, not just an architectural one. This whole product exists to eliminate paying for compute that isn't earning its keep — running a second, always-on scheduler instance (active-passive) or two simultaneously-active ones (active-active) purely as insurance against a multi-second restart would mean paying for exactly the kind of idle, always-on capacity this tool is built to help you stop paying for, just moved from your managed fleet onto the tool's own infrastructure instead. The model actually used costs nothing extra to run: one process, under whatever process supervisor already ships with the host operating system, on the one machine you're already running this from.

Deliberately absent, at every layer, is a second, simultaneously active scheduler process.

9.3 Installing and Configuring

A self-hosted tool means there's a genuine install step — brief, and the same on every deployment.

The quick way: install.sh. On a fresh host (Ubuntu 24.04 LTS is the recommended choice; any systemd distribution with Python 3.10 or newer and apt, dnf or zypper works the same way), clone the repository and run sudo ./install.sh install. It installs the system packages, creates a dedicated unprivileged service user, sets up the Python environment, asks for the settings in the table below and writes them to .env (readable only by that user), creates the deployment's SSH key (Part VIII.1) — or takes an existing one with --ssh-key — and builds the dashboard. With --domain <name> it also installs Caddy and serves the dashboard at https://<name>, with a certificate Caddy obtains and renews itself (the name's A record must point at the host, and ports 80 and 443 must be open). It then installs the poller and the API server as supervised services, plus an hourly backup timer (Part V), starts them, and prints the deployment's public SSH key, which every managed instance must trust. With --backup-ssh-key it also stores that key in Object Storage, encrypted with a passphrase you choose. Re-running it later updates the code and restarts the services, keeping the configuration, key and database. install.sh recover is the same procedure on a replacement host, with everything restored first (Part V.7). The rest of this section describes the same steps done by hand.

The tool is a plain Python program with no database server, no message queue, and no other infrastructure of its own to stand up. Cloning the repository, creating a virtual environment, and installing its dependencies is the entire installation:

9.4 Deploying on Kubernetes Instead of a VM

The same application, packaged as a container, for customers who already run a Linode Kubernetes Engine (LKE) cluster and would rather run this tool there than provision a separate host.

Nothing about the tool itself changes between the two deployment models — the same SQLite registry, the same single-scheduler-process guarantee from 9.2, the same CLI, REST API, and dashboard. What differs is only how it's packaged and supervised: one Kubernetes Deployment, pinned to exactly one replica, runs the scheduler and the API server as two containers inside a single pod, sharing one persistent volume for the registry, lock files, and SSH host-key trust store. Running two containers in one pod, rather than two separate Deployments, is what lets both processes safely share that state — Kubernetes guarantees they land on the same node, the same trust boundary the VM model already relies on between two sibling processes on one host. A Recreate deployment strategy (the old pod fully stops before a new one starts) preserves the single-writer guarantee from 9.2 through an upgrade or a config change, the same way a plain process restart does on a VM.

Everything downstream of installation — scheduling, groups, manual override, disaster recovery, the security model — is identical to the rest of this guide regardless of which deployment model is in use, with two exceptions: the release copy and recovery drills (Part V.10) are built around install.sh on a VM, since on Kubernetes the container image itself is the release; and settings and the SSH key come from Kubernetes Secrets, so credentials are rotated by updating those Secrets rather than with rotate-credentials. The Operations Guide's DEPLOYMENT-LKE.md covers the actual commands (building the image, the manifests, exposing the API/dashboard, backups, upgrades).

One optional integration point exists for customers whose cluster already runs the separate, sibling Linode-LKE-Private-Network project — automation many LKE customers already deploy to give cluster nodes a private VLAN/VPC network interface. That project installs an admission-time policy that automatically requires every new pod on the cluster to land on a specially-labeled node, unless its namespace opts out. This tool's own deployment tooling detects whether that policy is present and asks, once, whether to run under it or opt out — a single namespace label is the entire integration surface. The two projects never share code, a database, or an API with each other; this tool's own job (calling the public Linode API to manage other instances) never requires a private network interface for itself, so opting out is the recommended default for most deployments.

9.5 Rolling Out to Production: Best Practices

The safest path from a fresh install to a large production fleet is a staged one: plan the inventory, stand up one well-configured deployment, pilot it on non-production instances for a week, prove it at your real scale, then onboard production in waves.

None of what follows changes how the tool behaves — it is guidance on how to deploy and operate it so that the first time you discover something about your own fleet (an instance on local disk, a plan with little regional capacity at 9am, an application that needs a clean shutdown) it happens in a pilot, not in production.

1. Before you deploy: know your fleet.

PracticeWhy
Inventory every instance you intend to manage: region, plan, networking (public, VPC, VLAN), whether it boots from local disk or a Block Storage volume, and its data volumes.Instances on local disk need a one-time migration (Part II.2) with real downtime — plan maintenance windows for them up front. Instances with only VPC/VLAN interfaces need the scheduler to have network reachability into that VPC (Part I.4).
Confirm every instance runs a supported OS (Part II.3) with cloud-init and the Akamai datasource (23.3.1 or later, or an older build with the datasource backported).Every recreate re-applies the instance's network configuration through cloud-init; an image without it can't be onboarded.
Agree schedules and timezones with each application's owners, and group instances that share a schedule.Groups (Part III.1) keep a large fleet manageable; an individual schedule should be the exception, not the rule.
Decide which instances need a pre-stop hook or a post-start check (Part IV.3) — databases, queues, anything with in-memory state or a slow warm-up.A clean shutdown before every stop, and a real readiness check after every start, is the difference between "the VM came back" and "the application came back."
Check your Linode account limits against your peak fleet: running instances, Block Storage volumes, and reserved IPs, all at the same time.Every managed instance keeps its volumes and reserved IP permanently, and at the morning start every scheduled instance exists at once. Ask Linode support to raise limits before onboarding, not during.
For large fleets, confirm regional capacity for the plans you use at your peak start time.A start is a real instance creation. If a region is briefly short of a plan, the start fails and is retried for up to an hour (Part III.3); for many instances of one plan at one moment, stagger start times.

2. The deployment itself.

PracticeWhy
Run one deployment per Linode account, on a small dedicated VM (or one LKE deployment, 9.4) in the same region as the fleet.One scheduler process is the design (9.2); being in-region keeps API and SSH round-trips short.
Run the scheduler and the API server under a process supervisor (systemd Restart=always, or Kubernetes).Recovery from a crash or reboot is a restart, not a failover.
Use a dedicated API token with only the scopes the tool needs (9.3), not shared with other automation.Limits the blast radius of a leaked token, and keeps the tool's own request budget to itself.
Use one deployment-wide SSH keypair kept only on the scheduler host; add its public key to each instance yourself.The tool never needs, and should never be given, per-instance root passwords (Part VIII.1).
Allow SSH from the scheduler host to every managed instance (firewalls, VPC routing).Every start finishes with a real SSH reachability check, and every stop captures current SSH keys first.
Put the dashboard behind HTTPS (a reverse proxy) with "Login with Linode" configured; never expose it on plain HTTP.Anyone who can use the dashboard can start, stop, and offboard instances, and set hooks that run as root.
Configure Object Storage backup with a key scoped to its own bucket, and schedule backup (hourly or daily).This is what lets everything — including complex network setups, SSH keys, and hook scripts — be recovered after losing the scheduler host (Part V).

3. Onboarding and scheduling.

PracticeWhy

For a window that crosses midnight, use one overnight rule (a stop time earlier than the start time) rather than two rules split at midnight.One rule keeps the instance running straight through; two rules would stop it at midnight and start it again moments later.
For instances with only VPC/VLAN interfaces, run the scheduler inside the same VPC (or on the same VLAN).The scheduler reaches such an instance at its private address for every reachability check and key capture (Part I.4).

Appendix

Glossary

Terms of art used throughout this guide.

A.1 Terms of Art

reserved IP
A public IPv4 address held independently of any instance, so it survives that instance being deleted and can be reattached to whatever's recreated in its place. Permanently locked to the region it was first reserved in; carries a small charge while unattached.
golden template / template volume
A Block Storage volume holding a fully prepared OS image, cloned once per new logical instance at onboarding (Path A).
legacy interface model / newer interface model
The two mutually exclusive ways a Linode instance's networking can be configured — see Part I.3.
manual override
Starting an instance manually outside its own configured schedule window; arms an auto-revert countdown (Part IV.1).
schedule group
A named, shared schedule several instances can follow at once; an instance's own individual schedule, if enabled, always overrides its group's (Part III.1).
rebuild
The disaster-recovery command that reconstructs the local registry entirely from tags recorded on live Linode resources (Part V).
Path A / Path B
The two onboarding routes — a fresh instance from a template, or an existing instance migrated onto a volume in place (Part II).
unreachable
A status meaning a real instance exists but hasn't yet passed its network reachability check — either because it just started and the check hasn't completed, or because it was found powered off out-of-band. Resolved by simply running start again (Part 5.3).
pending deletion
An offboarded instance or deleted backup whose resources are kept, marked with lis-pending-* tags, until its grace period ends; it can be recovered until then (Part V.9).
needs_manual_recovery
A status meaning disaster recovery restored an instance's identity but couldn't determine its network configuration or SSH access from tags or Object Storage alone. Resolved by booting the instance once manually, then running onboard again (Part 5.3).
